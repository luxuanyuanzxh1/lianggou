## 二、为什么需要桥接

两套库的表名、字段完全不同，不能互换：

| 你的主库 | QuantWeave 后端期望 |
|---|---|
| `fact.price_bar(bar_date, instrument_id, adjustment, open…close, volume, volume_unit)` | `daily_bar(date, instrument_id, open…close, volume, amount)` |
| `master.instrument(instrument_id, code, exchange, name, asset_type, asset_subtype)` | `instrument_master(instrument_id, market, code, name, asset_type, exchange, source, updated_at)` |

所以新增 `scripts/build_local_dataset.py`：**只读 ATTACH** 你的主库，按后端 schema 重映射生成桥接库。
源库只读打开，绝不写入、不修改，构建耗时 **3.7 秒**。

## 三、口径映射（关键，4 条）

| # | 字段 | 处理 | 说明 |
|---|---|---|---|
| 1 | `date` / 价格 | `bar_date`；只取 `adjustment='raw'` | 后端全市场回测本来就标注 `price_adjustment: unadjusted`，与主库 raw 同口径 |
| 2 | `volume` | **÷100（股 → 手）** | 主库 `volume_unit='share'`；服务器库用「手」。实测 600519 @2026-08-03：本地 3,614,700 股 → 36,147 手，服务器 36,146 手 |
| 3 | `amount` | **派生**：`volume(股) × (high+low+close)/3` | 主库 `price_bar` **没有成交额字段**。实测 49.02 亿 vs 服务器真实 48.99 亿，**误差 +0.07%**，只影响流动性/换手类排序 |
| 4 | 周/月/季/年线 | 由 `daily_bar` 聚合派生 | 主库无周期线；后端 K 线周期切换要用，按周/月/季/年 `date_trunc` 聚合，行数 345 万 / 82 万 / 28 万 / 7 万 |

`instrument_master.market` 后端未参与查询，按 `SH=1 / SZ=0 / BJ=2` 填占位值。
`asset_type` 直接取主库字段（本地只有 stock 5,534 + index 2，无 fund）。

## 五、实测验证（同一套 preset，两套数据对比）

`presets.standard_multifactor`（14 个积木块，沪深京全市场，8 只等权，2023-10-09 ~ 2026-10-09）：

| 指标 | 服务器副本 | **本地库** | 差异来源 |
|---|---|---|---|
| universe | 5,546 | **5,534** | 主库少 12 只（无基金/退市股） |
| ST 剔除 | 208 | **201** | 静态名称判定差异 |
| daily_rows | 3,727,464 | **3,754,373** | 主库同期行数略多 |
| 总收益 | +146.05% | **+136.10%** | amount 派生 + 证券集差异 |
| CAGR | 34.99% | **33.15%** | 同上 |
| Sharpe | 1.00 | **0.94** | 同上 |
| MDD | -46.76% | **-43.75%** | 同上 |
| 成交笔数 / 胜率 | 908 / 56.81% | **923 / 54.60%** | 同上 |
| 耗时 | 25.5 s | **26.5 s** | — |

单票交叉验证（600519，2026-08-03）：开 1350.60 / 高 1363.35 / 低 1346.00 / 收 1358.98 —— **与服务器完全一致**。
两次重复提交结果数值完全相同（run_id `20261020-012256-747aed`），可复现。

**结论**：链路真实读的是本地库（证券数、覆盖度、行数都对得上），不是服务器副本；差异集中在
「无基金/无板块 + amount 派生」，属于数据源本身的边界，不是 bug。

## 六、日常怎么用

```bash
cd <项目根目录>

# 1) 启动（等同双击 启动.command）
./启动.command

# 2) 主库更新后刷新桥接库（3.7 秒，可反复跑）
env -u NODE_OPTIONS -u PYTHONPATH .venv/bin/python scripts/build_local_dataset.py

# 3) 换一个源库（移动硬盘 / 另一台机器同步过来的 .duckdb）
env -u NODE_OPTIONS -u PYTHONPATH .venv/bin/python scripts/build_local_dataset.py \
    --source /path/to/你的主库.duckdb

# 4) 只用某段区间，省磁盘
... --start 2018-01-01

# 5) 回到服务器副本
QW_DATA_DIR="$PWD/data" ./启动.command
```

访问入口：<http://127.0.0.1:3100/backtest>　（API 健康检查 <http://127.0.0.1:8767/health>）

## 七、已知偏差（用之前必须知道）

1. **数据只到 2026-10-09**，比服务器副本少 9 个交易日。主库更新后重跑第 2 条命令即可。
2. **成交额是派生的**（典型价近似 VWAP），误差 0.07% 量级。凡是以 `amount` 做硬门槛的因子，边界值会轻微漂移。
3. **没有基金与指数行情**：本地仅 5,534 只股票 + 2 个指数壳（`SH.000300`/`SH.000001` 只有 instrument 记录、无行情）。
   基准必须自建（后端已有市值加权 Top300 逻辑）。
4. **没有板块/概念/特征表**：`sector_member`、`concept_daily_bar` 等建了空表占位，
   凡依赖板块轮动、概念指数的积木块在本地库下会取不到数据。`feature_store` 仍是服务器副本（停在 **2026-08-17**），
   但回测主链路是**实时从 `daily_bar` 算因子**的，不依赖它。
5. **复权**：本地库 `qfq`/`hfq` 序列有 906 只标的历史因子崩坏（BJ.920593 的 qfq 2023-04 只有 3.7e-11）。
   全市场回测走 raw 不受影响，但 K 线页切「前复权/后复权」时会出现异常跳空。
6. **ST 判定是静态的**：用 `master.instrument.name` 的当前名称，历史 ST 期间的涨跌停幅度无法还原
   （ST汇洲 2023-2024 实际按 10% 交易，按当前 5% 口径会误判除权）。

| 配置 | 体积 | 冒烟结果 | 缺什么 |
|---|---|---|---|

`build_local_dataset.py --with-valuation` 会把源库的长表 `fact.market_value`（6,519 万行）
转成宽表 `market_value_daily`，一行一天四个字段：

| 列 | 含义 | 样例（600519 @2026-10-09） |
|---|---|---|
| total_mv | 总市值（元） | 1,578,853,000,000 |
| float_mv | 流通市值（元） | 1,578,853,000,000 |
| pb | 市净率 | 6.28 |
| pe_ttm | 滚动市盈率 | 19.39 |

- 行数 16,313,375，PE 覆盖 **99.64%** 的日线行，质量标记全部 `accepted`。
- 体积代价：market_data 从 716 MB → **1,138 MB**（+422 MB）。
- **注意：现有 54 个因子块全是价量类，代码里没有任何地方读 PE/PB/市值**（`grep pe_ttm|market_value` 零命中）。
  这张表目前只是「数据已就位」，要让估值真正参与排序，还需要新增一个估值因子块
  （`lego_pipeline._feature_sql` + catalog 元数据）——属于功能性开发，不是配置开关。

### 刻意没打进去的

- `feature_store.duckdb` 2.5 GB：只有 `precompute.py` 用，回测实时算因子
- `minute_bars.duckdb` 25 MB：仅 155 只、只到 2026-07，`14:45 执行` 块本来就需要全市场分钟价

### 打通过程中踩的坑

1. **`node: command not found`**：runtime 用 `python:3.13-slim`，没有 Node。改为从 web 阶段
   `COPY --from=web /usr/local/bin/node`；先验证过基础镜像自带 `libstdc++.so.6` 与 `libgcc_s.so.1`，否则 Node 会起不来。
2. 前端 `npm run build` 走的是 `zsh scripts/run_next_build.sh`，容器里没 zsh → 直接用 `npx next build`。
3. 单端口方案成立的前提是 `next.config.ts` 里的 `rewrites`：浏览器只访问 3100，`/api/v1/*` 由 Next 反代到容器内 8767。
4. `output: "standalone"` 才能把 node_modules 从 1.1 GB 压到只带被引用部分；standalone 仍需要 `.next/static` 与 `public` 一起拷。
